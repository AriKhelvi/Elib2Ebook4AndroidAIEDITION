# Вход RanobeLib/LibSocial: журнал OnePlus от 19 ноября

## Какие запуски разобраны

Первый файл `E2E-diagnostics-20261119-222509.txt` относится к OnePlus CPH2663,
Android 16 и стабильной версии 0.2.3. Владелец подтвердил включённый VPN.
Вложенная история входа была краткой и не показывала HTTP-переходы.

Следующий присланный текст содержит обычную диагностику 0.2.4-alpha.codex.1
(коммит `0a933bf`), начатую в 22:45:51 +07:00. Из 153 проверок прошли 134,
не прошли 17, ещё две завершились предупреждениями. В нём уже есть 65 строк
истории скачивания RanobeLib 6660. Это прежний запуск **0.2.3**, начатый
в 22:25:18 +07:00, а не попытка входа на альфе. Обе версии предшествуют
исправлению классификации ошибки OAuth в `997a052`.

Успешная анонимная проба книги RanobeLib 29609 проверяет скачивание двух глав
и обложки. Она не подтверждает вход или доступ аккаунта к книге 6660.

## Что видно в истории входа

1. Запрос подтверждения OAuth перенаправляется на `/auth/login` и получает HTTP 200.
2. Приложение отправляет `_token`, `login`, `password`. Сервер перенаправляет его
   на главную страницу RanobeLib, которая отвечает HTTP 200.
3. Повторный запрос подтверждения OAuth снова возвращает страницу входа.
4. Приложение принимает первую POST-форму за подтверждение доступа и повторно
   отправляет её на `/auth/login`, уже только со скрытыми полями.
5. После второго перехода на главную страницу OAuth-кода нет. Задание останавливается.

В этой цепочке только HTTP 200/302. Отказа TLS, HTTP 403 или HTTP 429 в ней нет.
Предыдущее исправление HTTP-классификации само по себе этот случай не устраняет.
Смена VPN не исправляет неверный выбор формы в приложении.

## Текущая форма сайта

19 ноября публичная [страница входа LibSocial](https://auth.lib.social/auth/login)
содержала поля `_token`, `login`, `password` и виджет
`altcha-widget name="altcha" challengeurl="https://auth.lib.social/altcha/challenge"`.
Приложение не формировало поле `altcha`.

Повторная анонимная проверка 22 ноября подтвердила тот же виджет, адрес задания
и схему ответа SHA-256 с `maxnumber=100000`; данные аккаунта не отправлялись.

Анонимный запрос задания ALTCHA вернул схему v1: `algorithm`, `challenge`, `salt`,
`signature`, `maxnumber`; алгоритм SHA-256, верхняя граница 100000.
По [официальному алгоритму v1](https://github.com/altcha-org/altcha-lib/blob/main/src/v1/index.ts)
клиент находит целое число, для которого хеш строки `salt + number` совпадает
с `challenge`, затем отправляет исходные поля и найденное число в base64 JSON.
Задание и подпись не требуют секретного ключа клиента; подпись проверяет сервер.

Это подтверждённое отличие протокола приложения от текущей формы. Оно объясняет,
почему нужно изменить вход, но не доказывает, что сервер отклонил историческую
попытку именно по этой причине: тело ответа формы в пользовательском журнале отсутствует.

## Границы исправления и проверки

Изменение общего загрузчика в `src/` необходимо: именно он формирует запрос входа
для RanobeLib и остальных сайтов LibSocial. Поддержка ALTCHA применяется
только при наличии виджета в форме входа; без него дополнительный запрос не нужен.
Формы входа, выхода и дополнительного кода не отправляются как подтверждение OAuth.
Для подтверждения выбирается POST-форма с CSRF и действием в `/auth/oauth/`.

Ответ задания ограничен 16 КиБ, чтение после заголовков — 30 секундами (или меньшим
таймаутом клиента), вычисление — 10 секундами. Поддерживаются отмена и проверка
адреса сервера входа. Пароль, cookies, задание и результат ALTCHA не записываются
в журнал; произвольные тела ошибок формы и выдачи токена тоже исключены.
Проверка сертификатов сохраняется.

Полноценный вход с реальным аккаунтом на телефоне остаётся отдельной проверкой.
Успех подставных HTTP-сценариев и сборки APK не означает, что эта проверка пройдена.
Сетевые таймауты остальных сайтов в диагностике также не устраняются этим изменением.
